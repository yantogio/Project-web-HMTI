Selamat pagi/siang Bapak/Ibu. Pada kesempatan ini, saya ingin memaparkan detail rancangan arsitektur dan logika sistem untuk proyek skripsi saya, yaitu **Sistem Informasi Manajemen Keanggotaan dan Keuangan HMTI Berbasis Web**.

Sistem ini saya rancang menggunakan arsitektur *Full-Stack* yang memisahkan secara penuh antara sisi *Client* (Frontend) dan *Server* (Backend). Pemisahan ini (*Decoupled Architecture*) bertujuan untuk memastikan aplikasi memiliki skalabilitas yang tinggi, keamanan yang berlapis, serta kemudahan dalam pemeliharaan kode di masa depan.

Berikut adalah rincian teknis dari masing-masing sisi aplikasi:

### 1. Arsitektur Backend (Server-Side)

Untuk membangun *Application Programming Interface* (API), saya menggunakan framework **NestJS** berbasis Node.js dan TypeScript. Pemilihan NestJS didasarkan pada arsitektur modularnya yang menerapkan prinsip-prinsip *Software Engineering* berstandar industri (*Enterprise-ready*).

Di sisi basis data, saya menggunakan **SQLite** yang dikelola melalui **Prisma ORM (Object-Relational Mapping)**. Penggunaan ORM ini sangat krusial untuk mencegah serangan *SQL Injection* sekaligus menjaga integritas relasi antar data. Logika bisnis utama di backend meliputi:

* **Skema Relasional Kompleks:** Basis data dirancang tidak hanya untuk sekadar mencatat kas masuk dan keluar. Saya memisahkan entitas `Transaction` dan `Dues` (Tagihan). Hal ini memungkinkan sistem untuk melacak secara spesifik anggota mana yang masih memiliki tunggakan (*UNPAID*), membayar sebagian (*PARTIAL*), hingga memiliki saldo lebih (*OVERPAID*) berdasarkan periode bulan dan tahun.


* 
**Konfigurasi Keuangan Dinamis:** Terdapat model `FinanceConfig` yang memungkinkan pengurus untuk mengatur besaran iuran per bulan, biaya denda, serta tanggal jatuh tempo secara dinamis melalui *database*, tanpa perlu mengubah (*hardcode*) sistem inti.


* **Keamanan Terpusat (RBAC):** Keamanan sisi server dijaga menggunakan autentikasi *JSON Web Token* (JWT) dan *Role-Based Access Control* (RBAC). Sebagai contoh, *endpoint* untuk membuat transaksi baru diproteksi secara ketat sehingga hanya pengguna yang memiliki *role* sebagai 'bendahara' yang dapat melakukan perubahan data kas organisasi.

### 2. Arsitektur Frontend (Client-Side)

Di sisi antarmuka pengguna, saya menggunakan **Vue.js versi 3** yang di- *build* menggunakan **Vite** untuk menjamin performa aplikasi yang cepat dan reaktif (*Single Page Application*). Pendekatan *Mobile-First Design* diterapkan menggunakan framework **Tailwind CSS** agar aplikasi tetap nyaman diakses melalui perangkat *mobile* maupun *desktop*.

Terdapat tiga mekanisme utama yang saya terapkan untuk mengelola alur data dan keamanan di sisi *client*:

* **Manajemen State (Pinia):** Saya menggunakan **Pinia** sebagai pusat penyimpanan data global (*Single Source of Truth*). Sesi *login* pengguna dan token akses disimpan secara persisten di `localStorage`, sehingga sistem dapat menjaga status autentikasi pengguna meskipun halaman dimuat ulang (*refresh*).
* **Axios Interceptors:** Untuk efisiensi dan keamanan komunikasi dengan API, saya mengimplementasikan *interceptor*. Mekanisme ini secara otomatis menyisipkan token JWT ke dalam *header* (*Bearer Token*) pada setiap permintaan data ke *backend*, sehingga data sensitif organisasi tetap terlindungi dari akses ilegal.
* **Navigation Guards:** Keamanan rute navigasi (*routing*) dikontrol secara ketat. Pengguna yang belum melakukan autentikasi akan secara otomatis dicegah mengakses halaman dasbor admin atau halaman keuangan, dan akan dialihkan ke halaman *login*.

### 3. Rencana Pengembangan (Software Development Life Cycle)

Saat ini, fokus utama pengembangan berada pada penyelesaian **Sistem Inti (Core System)** yang mencakup keamanan akses, sinkronisasi *state* aplikasi, dan automasi logika keuangan organisasi.

Untuk beberapa modul pendukung seperti halaman *DocsView*, *ShowcaseHub*, dan beranda publik (*HomeView*), saat ini telah selesai pada tahap perancangan antarmuka visual (UI). Modul-modul ini akan saya integrasikan secara bertahap dalam fase pengembangan lanjutan (*Continuous Integration*), mengingat fungsionalitasnya lebih berfokus pada penyajian informasi statis organisasi dibandingkan pengolahan logika transaksional.

Dengan perancangan arsitektur seperti ini, saya berharap sistem dapat menjadi solusi komprehensif untuk transparansi administrasi HMTI, sekaligus menjadi representasi implementasi teknologi *web* modern yang layak untuk diuji dalam penelitian skripsi ini.

Izin menjelaskan Pak, FinanceConfig merupakan tabel referensi global yang menyimpan parameter kebijakan organisasi. Hubungan antara tabel ini dengan tabel Dues bersifat Logic-Based, bukan Schema-Based. Sistem akan mengambil nilai nominal dari tabel Config hanya pada saat proses pembuatan tagihan (Generate), sehingga integritas histori keuangan tetap terjaga meskipun parameter konfigurasi diubah di masa depan.
